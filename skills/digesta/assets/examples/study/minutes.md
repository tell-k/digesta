### 2. SQL の実行計画を読もう(ソラさん)

約15分。PostgreSQL 16 を例にした。

- 概要: 遅い SQL の原因を EXPLAIN の結果から探す手順を、社内の注文一覧画面の改善を例に説明した。
- ポイント:
  - 注文一覧画面の表示に 3.2秒かかっていた。遅い原因は、画面を見ても分からない。データベースが SQL をどう実行したかを見る必要がある。
  - EXPLAIN は、データベースが立てた実行計画を表示する。EXPLAIN ANALYZE は SQL を実際に実行し、計画と実測を並べて表示する。
  - 見るところは3つ。どの処理に時間がかかっているか(actual time)、推定の行数と実際の行数がずれていないか(rows)、何回繰り返されているか(loops)。
  - 注文一覧の SQL では、orders テーブル約120万行を Seq Scan(全件の読み込み)していた。条件は user_id と created_at だった。
  - (user_id, created_at) の複合インデックスを作ると Index Scan に変わり、実行時間は 40ms になった。
  - 推定の行数が実際と大きくずれているときは、統計情報が古いことが多い。ANALYZE コマンドで統計情報を更新する。
  - EXPLAIN ANALYZE は SQL を本当に実行するので、UPDATE や DELETE に使うときは BEGIN と ROLLBACK で挟む。
- 質疑:
  - Q.(ハルさん)インデックスはたくさん作ったほうがよいのか。
  - A. 作りすぎると、書き込みが遅くなり、容量も増える。使われていないインデックスは pg_stat_user_indexes で探せる。
  - Q.(ユキさん)ORM を使っていると、SQL が見えないのでは。
  - A. 開発環境で SQL をログに出し、それを EXPLAIN に貼っている。
  - コメント(リクさん): 推定と実際の行数のずれを見る、というのはすぐに使えそう。

約10分。

- 概要: 静岡で開かれた技術カンファレンスに、東京から自転車で2日かけて行った記録。帰りは輪行(自転車を袋に入れて電車に載せる)で戻った。
- ポイント:
  - 運動不足の解消を兼ねて、前から気になっていた「自転車でカンファレンスに行く」を試した。
  - 日程: 8月20日(木)朝に東京の日本橋を出発し、小田原で1泊。21日(金)に箱根峠を越えて、沼津経由で静岡へ。22日(土)がカンファレンス。23日(日)に輪行で新幹線に乗って帰った。距離は1日約90km、2日で約180km。
  - 荷物はバックパック1つ、約7kgに絞った。着替えは2日分だけ持ち、宿のコインランドリーで洗った。
